# Customer app API gaps - answers and status (2026-10-13)

Reply to the customer-app team's 15 points. "Built" means implemented, tested against a real database and documented in Swagger. Nothing here was committed or pushed.

## P1 - blocks screens already built

| # | Ask | Status | Detail |
|---|---|---|---|
| 1 | Worker reviews for customers | **Built** | `GET /api/v1/search/workers/{workerId}/ratings?page&limit` -> `{ data: [{ score, comment, createdAt, reviewerFirstName }], meta: { page, limit, total } }`, newest first. `comment` is null when only a score was given. `reviewerFirstName` is the first word of the reviewer's profile name (null if none). Nothing else about the reviewer or booking is returned. Reviews hidden by moderation are not listed (and return when restored). 404 `WORKER_NOT_FOUND` for an unknown worker and for one not currently visible to customers (identical answer, same rule as the profile), 400 for a malformed id or paging, 401 without a token, 403 for a worker/admin token. Needs sign-off: customers could not read ratings before (Q-60); FR-WD-003 requires a rating/review summary on worker cards. |
| 1b | Rating scale | **Built** | `GET /api/v1/reference-data` now returns `ratingScaleMax` (the configured `RATING_SCALE_MAX`; reviews are whole numbers 1..`ratingScaleMax`; `rating.average` is on the same scale, 2 decimals). |
| 2 | Response schemas | **Built** | Every controller response in `service-categories`, `service-areas`, `customers/me`, addresses, `shortlist`, `bookings`, interviews, ratings, notifications, safety, support, verification, workers, etc. now publishes its 200/201 schema (`common/swagger/api-responses.ts`; the project does not use the Swagger CLI plugin, so they are explicit). Some inline-typed bodies (for example `{ unread: number }`, `{ updated: number }`, health) are still undocumented. |
| 2a | List envelope | **Confirmed** | Every paginated list is `{ data: T[], meta: { page, limit, total } }`; `total` is always present. Defaults page=1, limit=20, max limit 100 (`limit=0`, `limit=101`, `page=0` -> 400). Unpaginated lists are plain arrays: `GET /customers/me/addresses` returns `AddressResponse[]`, `/bookings/{id}/replacement-chain` returns an array. |
| 2b | `GET /shortlist` entry | **Confirmed** | `{ workerId, addedAt, available, worker }`. For a worker no longer visible: `available: false` and `worker: null` (the entry stays so the customer can remove it; `DELETE /shortlist/{workerId}` is idempotent, 204). Visible: `available: true` and `worker` is the same card as search. |
| 2c | `category` filter | **Confirmed** | `/search/workers?category=` takes the category **code** (for example `HOUSE_MAID`, `COOK`), with `areaId` (uuid). 422 `CATEGORY_NOT_AVAILABLE` / `AREA_NOT_AVAILABLE` for unknown or disabled values. |
| 3 | Test customer + fixtures | **Partly** | Static OTP already exists for staging: set `ALLOW_TEST_OTP=true`, `TEST_OTP_NUMBERS=+91...` and `TEST_OTP_CODE=<digits>` on the server (staging/demo only: it is allowed in any environment but prints a loud start-up warning, so never enable it for real users). Fixture data: `scripts/seed-demo.ts` (local database only; it refuses any non-local `DATABASE_URL` by design, and uses the real bucket for KYC PDFs) now also gives every third worker COOK as a second category, gives customer 0 two addresses (`Home` default and `Office` with line2/state), and shortlists 2 workers for customer 0 and 1 for customer 1. It was **not run** here (needs a bucket and Super Admin credentials), so the fixture is untested. I did not and will not seed the remote staging database from this machine. ## P2 - designed features

| # | Ask | Status | Detail |
|---|---|---|---|
| 4 | `GET /pricing/guidance` | **Built (admin-entered data)** | `GET /api/v1/pricing/guidance?category=COOK&engagement=PART_TIME&areaId=` -> `{ minMinor, maxMinor, period, basis }` (paise; `period` is HOUR, DAY, MONTH or ONE_TIME). An area-specific band wins over the category-wide one; **404 `PRICING_GUIDANCE_NOT_FOUND`** when none is set, so the app hides the card. The numbers are not derived from bookings (too few and no agreed period, Q-39): an administrator enters them with `PUT /api/v1/admin/pricing-guidance` (permission `category.manage`; `GET` lists, `DELETE /{id}` removes). Until someone enters bands the endpoint answers 404. |
| 5 | Budget and days in search | **Decision: not a filter** | Budget stays a label on the booking request (`budgetMinMinor`, `budgetMaxMinor`, `budgetPeriod`): worker `expectedSalary` has no period, so a budget filter cannot be correct (Q-39). `startDate` IS used by search (workers already booked for an overlapping time are left out). Days of the week are not matched: worker availability is time-of-day only (no per-weekday windows are specified), so sending days would be ignored. |
| 6 | `GET /home` | **Built** | `GET /api/v1/customers/me/home` -> `{ activeBooking, upcomingInterview, unreadNotifications, shortlistPreview[5], shortlistTotal }` (`activeBooking` = newest booking not COMPLETED/CANCELLED/REPLACED; `upcomingInterview` = next CONFIRMED interview/trial; both null when none). Customer-only. |
| 7 | Interview/trial endpoints | **Built (booking-centred)** | An interview belongs to a booking that already has the chosen worker: `POST /api/v1/bookings` with `workerId` first, then `POST /api/v1/interviews { bookingId, type: INTERVIEW or TRIAL, preferredAt (ISO 8601), note? }` (Idempotency-Key supported). `GET /api/v1/interviews?page&limit&status&type` lists all my interviews across bookings (new), `GET /api/v1/interviews/{id}`, `POST /interviews/{id}/reschedule` `{ preferredAt }`, `/cancel` `{ reason? }`, `/complete`, `/accept-proposal`, `/reject-proposal`. The worker answers with accept, decline or propose. Statuses: REQUESTED, CONFIRMED, RESCHEDULE_PROPOSED, DECLINED, CANCELLED, COMPLETED (labels in `GET /reference-data` `statusLabels.interview`). **Free times:** `GET /api/v1/search/workers/{workerId}/slots?date=YYYY-MM-DD` -> `{ date, slotMinutes: 60, horizonDays: 14, slots: ['09:00', ...] }`; an interview is one hour. |
| 8 | Customer profile photo | **Out of scope** | FR-CUS-001..006 (SRS 3.2) and FRD FM-02 contain name, email, addresses and language only; no customer photo is specified or built. Needs a product decision if wanted. |
| 9 | Address label/line2/state | **Built** | `label` (max 50), `line2` (max 500), `state` (max 100) on create and update; all optional; `null` clears on update; returned on every address response. Migration `20261018090000_customer_address_label` (additive). |
| 10 | Coordinates -> area | **Built (admin-set centres)** | `GET /api/v1/locations/service-area?latitude&longitude&name&city` -> the area `{ id, name, city }`; the nearest enabled area whose circle covers the point wins, otherwise an exact case-insensitive `name` match; **404 `AREA_NOT_FOUND`** when neither matches (the customer then picks from the list). Areas have no polygons: an administrator sets `centerLatitude`, `centerLongitude`, `radiusMeters` (100..100000, all three together or all null) on `POST/PATCH /admin/service-areas`. Areas without a centre resolve by name only. |

## P3 - confirmations (from the code)

| # | Question | Answer |
|---|---|---|
| 11 | OTP error codes | Expired or never requested: **400 `OTP_EXPIRED`**. Wrong code: **400 `OTP_INVALID`** (message says attempts remaining). Too many wrong codes: **429 `OTP_ATTEMPTS_EXCEEDED`** (this response starts the lock), while locked: **429 `OTP_LOCKED`**. Request side: 429 `OTP_RESEND_COOLDOWN`, `OTP_SEND_LIMIT`, `OTP_RATE_LIMITED`. Every OTP 429 carries `details[0] = { field: "retryAfterSeconds", messages: ["<n>"] }` in the error envelope (no `Retry-After` header on these). The generic IP throttle returns 429 `RATE_LIMITED` and its own `Retry-After` header. |
| 12 | Default address and error codes | The first address is **not** auto-default; `isDefault: true` on create or `PUT /customers/me/addresses/{id}/default` replaces the current default (idempotent). Deleting the default leaves the customer with no default until they choose one. Delete is a soft removal and is never blocked by a booking (bookings keep their address), so there is no "in use" code. Unknown or someone else's address: 404 `ADDRESS_NOT_FOUND`. Addresses are not validated against service areas; an unserviceable area shows up when creating a booking: 422 `AREA_NOT_AVAILABLE` (or `CATEGORY_NOT_AVAILABLE`, `WORKER_NOT_ELIGIBLE`). |
| 13 | `minRating` and `sort` | Built. `minRating` (1 to `ratingScaleMax`) keeps workers whose average is at least that value; workers with no rating are excluded. `sort` accepts `EXPERIENCE_DESC` (default), `EXPERIENCE_ASC`, `RATING_DESC` (unrated last); stable ordering, not a relevance ranking (Q-46). |
| 14 | `meta.total`, refresh | `meta.total` is always present in lists. `POST /auth/token/refresh` body `{ "refreshToken": "..." }`; response `{ accessToken, refreshToken, tokenType: "Bearer", expiresIn, user }`. The refresh token is single-use: store the new one every time; reusing an old one revokes the session (401 `REFRESH_TOKEN_INVALID`). Lifetime is absolute (not sliding). |
| 15 | `support.phone` / `support.email` | Configuration, not code: set `SUPPORT_CONTACT_PHONE` and `SUPPORT_CONTACT_EMAIL` on the server (documented in `.env.example`, currently unset on the environments I can see). I do not have the real contact details. |
