# Decision register (Q-77 to Q-93)

Updated 2026-10-13. For each open business question: the safe behaviour in the code today, options with trade-offs, and whether implementation can proceed without an answer. Nothing below has been decided by engineering: "safe current behaviour" is the least-assuming default. `C` = client decision, `U` = platform/infrastructure choice.

| ID | Question | Workflow affected | Safe current behaviour | Options and trade-offs | Can build without an answer? |
|---|---|---|---|---|---|
| Q-77 | Booking cancelled after the customer paid, or a payment that arrives after cancellation: refund or not, fee, deadline, who decides | Cancellation, payments, finance | Nothing refunded automatically. A payment exception is raised with amount, gateway references and states; staff with `payment.refund` refund in full; `payment.manage` closes it | (a) Full refund until the worker starts - simplest, customer friendly, platform absorbs gateway fees. (b) Fee-based (percentage or fixed) - protects the platform, needs a fee table and customer wording. (c) No refund after confirmation - clear, high complaint risk. Each needs a deadline rule and an owner | No. Everything else (alerts, exception queue, manual refund) is built |
| Q-78 | How long may a confirmed booking stay unpaid before it is cancelled; is the gateway order abandoned | Booking hold, payment, availability | Rule exists, off until `PENDING_PAYMENT_AUTO_CANCEL_HOURS` is set; an unpaid booking holds the worker until paid or cancelled | 30 min - frees workers quickly, risks cancelling slow payers. 2-24 h - friendlier, a worker can be blocked for hours. Same value should drive the alert (`PENDING_PAYMENT_ALERT_HOURS`) | Yes: set the two values in configuration when decided; no code change |
| Q-79 | Razorpay account: live KYC, auto-capture, methods, webhook events, partial refunds, refund speed | Payments | Test keys; auto-capture assumed; full refunds, normal speed | Owner task with Razorpay; partial refunds also need Q-77 | Live go-live: no. Code: yes |
| Q-80 | Who is alerted about money problems, by which channel, how fast; how long resolved items are kept | Operations | Admin alert inbox shows every payment exception to staff with `payment.manage`; notification only if a `PAYMENT_EXCEPTION_ALERT` template exists (none seeded) | Inbox only (zero setup); plus email/SMS to a finance group (needs a channel and template); on-call escalation | Yes |
| Q-81 | Malware scanning vendor, quarantine vs delete, retention of confirmed documents | KYC documents | Validate type, size, content, hash; rejected files deleted; confirmed files never deleted | Self-hosted ClamAV (adapter built, needs a server); a managed scanner (new adapter); quarantine bucket instead of delete (storage change) | Partly: scanning is optional and fail-safe; retention needs an answer (Q-88) |
| Q-82 | Real proxy topology per environment | Rate limiting | Production refuses to start without `TRUST_PROXY_HOPS`; template uses 1 | Render only = 1; CDN + Render = 2 | Yes (operator sets the value after checking headers) |
| Q-83 | Cancellation fee and automatic refund rules | Cancellation, payments | Fee 0, no automatic refund | Same options as Q-77 | No |
| Q-84 | How early may a service start before the agreed date | Booking start | `BOOKING_START_EARLY_DAYS=0`: not before; staff always can | 0 - strict. 1-2 days - flexible. Staff-only override (current) | Yes: configuration |
| Q-85 | What makes a customer VERIFIED | Customer profile, search trust | Interim rule: complete profile + one active address; staff decision is final (`CUSTOMER_AUTO_VERIFY`) | Keep interim; add address-document check; manual approval only (`CUSTOMER_AUTO_VERIFY=false`) | Yes: configuration |
| Q-86 | Who may see a worker's emergency contact and address, and when | Worker privacy, support | Any admin with `worker.view`; every read audited | Restrict to Verification Executive and Super Admin; reveal-on-reason with a time limit; show to the customer only after a confirmed booking (not built) | Yes for the audit; policy needs the answer |
| Q-87 | Admin MFA method and forgotten-password process | Admin access | Admin can change own password; Super Admin can set a temporary password for another admin; no MFA | TOTP app (no vendor, new tables); SMS OTP to the admin mobile (reuses SMS provider); email magic link (needs an email provider) | No |
| Q-88 | Data erasure and retention periods | Compliance | Deletion requests recorded for staff; nothing erased; audit logs and documents kept | Anonymise personal data after N days while keeping payment/audit rows; hard delete where law allows; separate periods for documents and logs | No |
| Q-89 | Is malware scanning required, which scanner | KYC documents | Optional ClamAV; readiness warns when off | Required before launch (deploy clamd) or accepted risk with type/size/content checks only | Yes |
| Q-90 | Maps provider and distance in matching | Search, matching | No maps; addresses keep optional coordinates | Google Maps (cost, best data); Mappls/Ola (India focus); none for V1 (area-based matching, current) | Yes (area-based works); distance needs the answer |
| Q-91 | Error monitoring tool and backup/restore targets | Operations | Health endpoints, alerts, structured logs; runbook | Sentry (new dependency); the host log service + uptime monitor only; backup retention days | Yes for the runbook; tool needs the answer |
| Q-92 | Travel time between two jobs; should an unpaid confirmed booking hold the worker and for how long | Availability, booking | `BOOKING_TRAVEL_BUFFER_MINUTES=0`; an unpaid booking holds until paid, cancelled or expired (Q-78) | 0 - tight schedules, workers may run late. 15-30 min - realistic for same-area jobs. Longer for cross-city. Holding while unpaid protects the customer's choice but can block workers | Yes: configuration |
| Q-93 | Engagement types each of the six categories offers; what "Monthly" means | Catalogue, search, booking | No list applied: every category accepts every engagement; the admin endpoint enforces any list that is set | Apply the PRD "typical" table as written; treat "Monthly" as full-time, or add a MONTHLY value (schema change); leave unrestricted | Yes: configuration through `PUT /admin/service-categories/{id}/engagements` |
